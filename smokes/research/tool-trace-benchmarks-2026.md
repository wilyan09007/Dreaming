# Public corpora of real agent tool-call traces, to extend S14 (research, 2026-10-17)

Scope: every public 2024-2026 corpus of agent tool-call traces found that could extend S14 (`smokes/s14_tool_traces/RESULTS.md`), plus published measurements of tool-call repetition and cacheability. Method and limits: WebSearch (extended) and WebFetch. In this container WebFetch reaches only GitHub; arxiv.org, huggingface.co, mdpi.com and alphaxiv.org fail with ENOTFOUND. So every GitHub fact below is from the repo page itself, and every arXiv, Hugging Face and blog fact is from a search-result summary, not the primary page. Those rows are marked "(search summary)". Nothing here was downloaded or run. "Unverified" means the field was not confirmed on a primary page.

## Bottom line

1. S14's open question is not "does prediction work" but "what is the repeat rate on traffic that is not a benchmark replayed 4-8 times". No public corpus found gives that. The only public traces with real returns and repeated runs of the same task are benchmark runs, so they bound the W (re-run) regime and say little about regime X. State this in S14b.
2. Add next (in this order):
   - (a) **MCPMark trajectory log** (`Jakumetsu/mcpmark-trajectory-log`, Hugging Face). Real Notion, GitHub, Postgres, Filesystem and Playwright MCP servers, k runs per task (the repo's example uses k=4), per-run folders with `execution.log`; the per-file layout (`messages.json` etc.) is unconfirmed: the README says only "JSON + CSV per task" under `run-*` (https://github.com/eval-sys/mcpmark, fetched). This is still the only found corpus with real, live-server returns and repeated runs of one task, but it is weaker than first stated. Per GitHub issue #272, opened 2026-10-03 (https://github.com/eval-sys/mcpmark/issues/272, fetched), the v1-0905 logs cover 11,314 runs of which 559 (4.9%) ended in a harness or API error with no verdict; they come from a deprecated task version ("Verified is now the default"); a median 22% of tasks flip between identical runs; and there are only 21-30 tasks per service. A search summary says the upload excludes the medium and high difficulty tiers, so it may be a subset only (unverified). Drop the errored runs before any count. Use it for a repeat-rate and flip-rate measurement per service, not as a drift or reset-controlled study: the README describes isolation and template re-creation but no per-run reset, and "every environment version-pinned" limits the external-state-drift pitch.
   - (b) **Exgentic agent-llm-traces** v1 (CDLA-Permissive-2.0) and v2 (HF). Reported to cover AppWorld, SWE-bench, BrowseComp+ and tau2 (airline, retail, telecom). Schema unconfirmed; likely LLM-span only. Both versions are described as OpenTelemetry traces of LLM calls: v1 "OpenTelemetry traces covering LLM inference" with harness, benchmark, models, token counts, session_id, spans and collected_at; v2 "filtered to the agent under test's chat-only LLM calls" (search summaries, https://huggingface.co/datasets/Exgentic/agent-llm-traces and https://huggingface.co/datasets/Exgentic/agent-llm-traces-v2). Tool returns exist at best inside LLM inputs, and tool timings at best as gaps between spans. A Sept 2026 paper replays it for LLM serving: 851 tau2 sessions, 9,031 LLM spans (search summary, https://arxiv.org/pdf/2608.12123). Confirm the schema on first download before committing S14b effort to it. If it is LLM-span only, use it for LLM-step timing and prompt-prefix analysis, not tool repeat rate; skip the tau2 slice either way (S14 covers tau-bench).
   - (c) **Microsoft GitHub Copilot coding-agent traces** (Azure/AzurePublicDataset release, CC-BY, GitHub-hosted, reachable now): 8.7M tool calls, 301K sessions, per-call tool name, status and duration (facts confirmed on the page, fetched). No arguments or outputs, so use it for the latency replication only, at 12x the volume of TraceLab (8.7M / 743,819 = 11.7x against v0.0.2). Do not use it for next-call speculation: S19 (`smokes/FINDINGS.md`) found speculation hides only 0.5-3% of time on coding-agent traces, and FINDINGS plan change 5 retargets speculation to the next LLM step.
3. HF-hosted corpora (a, b) cannot be downloaded from this container. Per the user's note, if only AWS is reachable, use a small AWS machine as the download relay (fetch from HF there, ship derived shards to the pod or repo). Do not plan around this until the AWS access is confirmed; TraceLab and Copilot (GitHub) need no relay. First relay job: pull the MCPMark logs (a), drop errored runs, and report repeat rate per service with run-to-run flip rates (median 22% of tasks flip between identical runs, issue #272); dump the Exgentic schema before spending S14b effort on it.
4. Do not add as "real return" evidence: Nemotron-Agentic (LLM-simulated returns), ToolBench-style simulated APIs, AgentDojo and third-party WebArena dumps (small, third-party, one run, models not the product's). BFCL, AppWorld leaderboard and SWE-bench/experiments have real or executable backends but their GitHub repos do not ship usable run logs (see table).
5. Published repetition numbers are weak. The tool-cache hit rates found are from training-time rollouts (TVCache, up to 70%, workload-dependent 14-74%; search summary, self-reported, unverified: the repo shows no hit rate) or synthetic Zipf workloads (hierarchical caching, ToolCaching; self-reported). The closest external prior for new-task traffic (regime X) is Agentic Plan Caching at a 0-12% hit rate on personal-agent tasks, and GPTCache 3.3% on synthetic tasks (Basu, https://arxiv.org/html/2602.18922v1, search summary, unverified), which agrees with S14 X (0-12% airline, 5-12% MCP servers). Use it as the external prior for X. No production measurement of tool-call repeat rate was found. The ">40% of tool invocations are repeated" claim is unsourced. S14b should say so and present its own number as the first measured on logged real runs.
6. S14b must report every cell as repeat rate x safe-repeat share, per corpus and per regime (W re-run, X new task), with tool-class split (read, write, pure, time-varying), TTL-needed share, and a cold-start curve by trial index. Exact table below.

## What this changes in the plan

- S14b should be framed as "does the S14 conclusion (benefit = repeat rate x safe share) hold on real servers with repeated runs". MCPMark logs are the best available fit, with the caveats above (errored runs dropped, deprecated tasks, 22% run-to-run flips, small task counts per service). They add live external state (GitHub, Notion) where the S14 Toucan finding of 33% time-varying tools can be tested with repeated runs; timestamps in `execution.log` are unconfirmed. Benchmark reruns bound only regime W; for X use the APC 0-12% prior and S14's own X numbers.
- Latency work (S14 F) should move from TraceLab alone to TraceLab plus Copilot traces (latency replication only; speculation stays on the next LLM step per S19 and FINDINGS plan change 5), with a cross-dataset check: train on one, test on the other. S14 found a 3-week drift gap; a second population tests whether "session history beats tool name" generalises.
- Do not spend effort on the other HF trajectory sets (nebius, SWE-smith, third-party AgentDojo/WebArena). They add volume, not a new regime.
- The repetition literature gives no external prior for "customer's own traffic". The Dreaming claim stays as in S14: report the customer's measured repeat rate, and show our public-corpus range as context only.
- Gap in infrastructure: HF is unreachable from the pod and container. Plan an AWS relay (a small instance that downloads from HF and uploads derived shards) before S14b; that fits the user's "use an AWS machine as a proxy" note, but this note did not test it.
