# S29 memory student at scale (RunPod RTX 4090 15 min $0.225, plus Modal CPU 4 min est. $0.03)

## In plain words

The question: is the Hopfield memory (a softmax(beta x cosine) vote over stored (embedding, label) rows, seeded with LLM-written example rows) a safe student once a call site has many labels and many rows? Five checks, all on frozen bge-small vectors, 500 calibration rows, `common.certify` (5% budget unless stated).

1. **Does the seeded memory tie LR on certified coverage at k = 3 and 10 rows per label?** Yes when every label is seeded and there are 45 to 77 labels: the differences to LR and to seeded LR are -0.09 to +0.25 at k=3 and k=10, none beyond 2 standard errors (Banking77, CLINC45, exactly k rows per label). **No at 150 labels**: on CLINC150 the memory certifies 0.28 to 0.33 less than LR at k=10 (2.3 to 3.9 s.e.) and 0.15 to 0.19 less at 50 and 100 rows per label (6 to 10 s.e.), with accuracy 3.5 to 4.3 points lower. Banking77 at the full 9,993 rows is a tie (Hopfield+seed 0.858 vs LR 0.835).
2. **Which imbalance rule wins?** Weighting each class's vote by 1/(its row count). On a Zipf-skewed memory (12 to 172 rows per class) it lifts accuracy from 0.880 to 0.905, rarest-20-class recall from 0.816 to 0.885 and coverage from 0.678 to 0.731, and costs nothing on balanced data (0.816 vs 0.824 coverage, within noise). Capping rows per class at query time (top 1 or top 5 by similarity) does not help (0.652 and 0.588 coverage).
3. **Query cost** (one CPU thread, batch 1, p50): 0.31 ms at 1k rows, 1.17 ms at 10k, 17.1 ms at 100k, 271 ms at 1M. On the GPU 0.2 to 0.4 ms up to 100k and 3.0 ms at 1M. An hnswlib index answers in 0.15 ms at 1M rows but changes 4.3% of predictions versus the exact read.
4. **How often does a deletion revoke the certificate?** Deleting every row of 10 labels revoked it in 4 of 5 splits (recertification found 0 coverage, because traffic for the deleted labels is now always wrong); deleting 20% random rows or every row containing a common token ("money", 10.7% of rows) revoked it in 1 of 5 splits each and cut coverage from 0.780 to 0.57 on average. Keeping the old cutoff without recertifying would have broken the 5% promise in the same splits (realized error 0.053 to 0.137). A refit LR is revoked about as often (5/5, 0/5, 1/5).
5. **Byte stability across processes:** yes. Three fresh Python processes give the same sha256 over all 3,076 read-outs on CPU (1 thread), and the same on GPU. Inside a process, repeats at a fixed batch shape are byte-identical on CPU for every head; what changes bytes is batch shape, CPU thread count (2, 4, 8 threads all differ from 1), and on the GPU an `index_add` (atomic) read (1,000 distinct byte strings in 1,000 repeats). Label plus confidence rounded to 3 decimals never changed. CPU and GPU do not agree byte for byte, nor on (label, confidence to 4 dp) for every query; how many queries differ was not measured.

So the memory is fine as the day-zero tier and as the hot spare at tens of labels, and its latency, deletion and replay properties hold. It should not be expected to win promotion at 150 labels with plenty of rows: there LR (or the prototype / HDC heads, which stay within 0.03 to 0.05 at k=10) certifies more.

## Setup

- **Script:** `run.py` (sections A, B, C, D, E as written before this run, plus the additions listed under "Changes to the script"). Tables: `tables.md` (main run) and `rerun/tables.md` (exact-k run), both generated by `report_s29.py`; raw cells in `results.json` and `rerun/results.json`; streamed logs `pod_launch.txt`, `log.txt`, `rerun/log.txt`, `rerun/modal_launch.txt`.
- **Data:** Banking77 (77 labels, 9,993 train, 3,076 test), CLINC150 in-scope (150 labels, 15,000 / 4,500), CLINC45 = the 45 CLINC labels that have cached LLM-written examples (4,500 / 1,350). Seed rows: `smokes/.cache/synth_examples.json` (761 Banking77 rows over all 77 labels, 450 CLINC rows over 45 labels). bge-small-en-v1.5, fp32, unit norm.
- **Protocol:** 5 splits; each split draws its training rows and a 500-row calibration slice from the test set (the rest of the test set is the holdout). Confidence = top-2 gap of the arm's class scores; certificate = `common.certify` (40-point grid, delta 0.05) on the calibration slice, applied to the holdout. Hopfield beta from {5, ..., 640} picked on calibration accuracy (ties: lower NLL). LR = multinomial, C=10, L-BFGS in float64 on the GPU (cross-checked against sklearn: argmax agreement 0.995 to 0.998, 5% coverage equal within 0.001; `tables.md`, LR cross-check).
- **Two ladders.** A: n rows drawn with at least one per label (`common.stratified_subsample`), Banking77 0 / 77 / 231 / 385 / 770 / 3,080 / 9,993, CLINC150 150 to 15,000, CLINC45 45 to 4,500. A_k: exactly k = 1 / 3 / 10 rows of every label. A's small sizes have uneven class counts, which hurts LR (its bias learns the skew: Banking77 LR accuracy drops from 0.594 at 77 rows to 0.549 at 231); A_k removes that, so the k=3/10 answer comes from A_k.
- **Hosts:** main run (A, B, C, D, E) on one RunPod RTX 4090 (secure cloud; community had no supply), torch 2.8.0+cu128, 80 CPUs, 512 s of compute in a 15.2-minute pod. A_k on Modal CPU (8 cores, torch 2.14.1) because two later pod launches (RTX 4090, RTX A5000) got "no instances available"; LR and the memory read are the same code on CPU.

### E: determinism (3,080-row Banking77 memory, beta 80, 1,000 repeats per test)

| test | CPU, 1 thread | GPU |
|---|---|---|
| same query, batch 1, fixed shape: distinct raw byte strings | 1 for every head | 1 for every head except the `index_add` read: 1,000 |
| same query inside random batches of size 1 to 8 | 2 for the float heads (dense and scatter Hopfield, prototype, LR); 1 for the integer heads (HDC, fixed-point Hopfield) | 3 dense Hopfield, 1,000 `index_add`, 2 prototype / LR, 1 integer heads |
| same query inside random batches of fixed size 8 | 1 | 1 (except `index_add`: 1,000) |
| same query from 8 threads, batch 1 | 2 (dense and scatter) | 1 dense, 1,000 `index_add` |
| distinct (label, confidence to 3 dp), any test above | 1 | 1 |
| torch threads 2 / 4 / 8 vs 1: same bytes? | no / no / no (batch 1 and batch 8) | - |
| 3 fresh processes, full dense read of 3,076 queries: distinct sha256 (raw / label + conf 4 dp) | 1 / 1 | 1 / 1 |
| CPU vs GPU, same process: same raw bytes / same (label, conf 4 dp) for every query | no / no | |
| hnswlib: repeats and random batches identical; rebuild with 1 thread identical; rebuild with 4 threads | 1.0 of neighbour lists identical; 0.9997 with 4 threads | |

The plan's replay rule (fixed row order, one CPU thread, fixed batch shape, confidence quantized before hashing) is what these numbers support: under it the memory read is byte-stable across processes. It should not run on the GPU with `index_add`, nor with more than one CPU thread, nor batch-size-dependent.

## Changes to the script in this run

- The datasets `Column` bug from the first launch (`btr + bte` on two `Column` objects) was already fixed in the committed `run.py` (texts converted with `str()`); verified by building the worlds locally with datasets 5.1.0 and on the pod.
- Added: k=3 sizes in every A ladder (231 / 450 / 135 rows); section `A_k` (exactly k = 1, 3, 10 rows per label); B arms "Hopfield cap1 / cap5" (top-m rows per class at query time, the plan's other imbalance rule); E cross-process check (3 fresh interpreters hash the full dense read on CPU and GPU); beta grid extended to 640 (training-plan 4.1); `S29_CPU=1` skips the CUDA gate for a CPU host (`modal_ak.py`). Run order is now A_banking, B, C, E, D, A_clinc, A_k so a timeout costs only the largest cells. The 1M-row index build is skipped if its estimate exceeds 4 minutes (it took 20 s).
- `smokes/pod.py`: reads `RUNPODKEY` from the environment when the project root has no `.env` (a git worktree), and then ships no `.env` to the pod.

## Not run, or cut

- Nothing was shrunk: 5 splits everywhere, 1,000 repeats in E, the 1M-row flat read and index all ran.
- The count of queries where CPU and GPU disagree on (label, confidence to 4 dp) was not measured: the code is in `run.py` (`cpu_vs_cuda` in the cross-process digest) but the rerun that would have run it on a GPU got no RunPod supply twice, and A_k went to Modal CPU without E.
- A_k ran on a different host (Modal CPU, torch 2.14.1) from the main run (RTX 4090, torch 2.8.0); both use float64 L-BFGS for LR and float32 for the memory read.
- Beta is picked on calibration accuracy, as the script was written, not on NLL as training-plan 4.1 says; and on the same slice that is then certified (selection optimism, as in S24/S27).
- 2% budget: almost nothing certifies at 500 calibration rows for any arm, so it says nothing about the arms.

## Caveats

- Coverage at a 5% budget with 500 calibration rows is noisy (s.d. 0.1 to 0.3 per cell at k=3/10), so "tie" at 45 to 77 labels means "no difference this run can see", not equality. The CLINC150 deficit is many standard errors and holds at both ladders and both budgets.
- The 1M-row memory is synthetic (tiled base rows plus noise); its latency is real, its recall and changed-prediction numbers are optimistic or pessimistic only as far as real near-duplicates differ from Gaussian jitter.
- Latency was measured on the pod's server CPU and an RTX 4090, not on Fly's shared CPU.
- B uses one world (Banking77) and one memory size (3,080 rows).

## Verdict

Keep the memory as priority 1 for what it is good at (no fit, forget by deletion, evidence rows, byte-stable replay, sub-ms reads up to ~10k rows on one core), seed it, and weight its vote by 1/class count. Do not expect it to beat LR at 150 labels with tens of rows per label; the parallel trainer's certificate will promote LR there, which is the design. Deleting whole labels revokes the certificate almost always, so a deletion request should trigger an immediate re-gate, not a quiet row drop. Past ~100k rows on one CPU thread a read costs ~17 ms, so either cap rows per site (HDC compaction) or use an index and accept that an approximate read changes about 2 to 4% of predictions and must not be what replay hashes.
